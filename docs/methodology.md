# Methodology

FinEval mirrors how model evaluation is actually done in AI-training work, made reproducible end to end. This document explains each stage and the design choices behind it.

## The pipeline

```
  1. datasets      →  2. task bank   →  3. rubrics    →  4. judge        →  5. score      →  6. report
  (ground truth)      (adversarial      (weighted        (human / LLM       (harness)         (scorecards +
                       prompts)          criteria)        pass-fail)                            comparison)
```

## 1. Datasets and ground truth

Two synthetic-but-consistent datasets are generated by `datasets/generate_datasets.py` with fixed seeds and fixed values. Because the data is generated, the **correct answer is known exactly and never drifts** — every rubric value is traceable to `datasets/ground_truth.json`. The evaluation method is identical to what you'd run on real public data; only the source of the numbers changes.

## 2. Task bank

Seven prompts, each written to be hard in a *specific* way — the places models predictably fail (confusing similar correlations, averaging ratios wrongly, stating correlation as causation, absolute vs percentage growth, totals that don't reconcile, missing an outlier). Designing prompts around known weaknesses is what makes an evaluation *discriminating* rather than easy to pass.

## 3. Rubrics

Each task has a weighted rubric (`rubrics/*.json`): positive criteria for the required results, negative criteria for the predictable mistakes. Rubrics are structured data so the harness can apply them mechanically. See [`../harness/rubric_schema.md`](../harness/rubric_schema.md).

## 4. Judging

A rater — a human (as here) or an LLM judge — reads a model's response and marks each criterion present or absent. Those judgments live in `responses/<model>.json`. **The judgment is where expertise lives; the scoring is where automation lives.** Separating the two keeps the process transparent: anyone can see which criteria a model met and recompute the score.

> The two model files here (`model_alpha`, `model_beta`) carry illustrative judgments that demonstrate the full pipeline. To evaluate a real model, run a task's prompt against it, mark the criteria, and drop the judgments into a new `responses/` file.

## 5. Scoring

`harness/score.py` computes, per task:

- **raw** = sum of signed weights for the criteria marked present,
- **score** = raw, floored at 0 (a task can't go negative),
- **max** = sum of the positive weights.

Overall = total score ÷ total max across the seven tasks.

## 6. Reporting and model comparison

The harness writes a detailed **scorecard** per model and a **comparison**. The comparison uses the **relative-advantage** metric:

```
relative advantage = (stronger score − weaker score) / stronger score
```

A gap of **≥ 15%** is the bar for confirming that a task set meaningfully separates a strong model from a weak one. In this run, model_alpha (92.9%) beats model_beta (45.9%) by a **50.6%** relative advantage — comfortably clearing the bar, because the weak model falls into exactly the traps the negative criteria were written to catch.

## Why it's built this way

- **Reproducible:** fixed data + structured rubrics + a deterministic scorer means the same inputs always give the same scorecard.
- **Transparent:** every point on a scorecard traces to one criterion and one judgment.
- **Discriminating:** the tasks and negative criteria are designed to expose real weaknesses, not reward surface fluency.
- **Portable:** swap in a new dataset, task, or model without changing the harness.
